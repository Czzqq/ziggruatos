# RISC-V TEE 设计路线

本文是未来设计与学习计划。当前仓库没有实现可信监控器、安全世界、可信应用装载或远程证明。SBI HSM、SMP 与原生 M-mode 小核不构成这些能力。

## 模块职责设想

| 组件 | 计划责任 | 必须明确的边界 |
| --- | --- | --- |
| 可信监控器 | 建立隔离、创建/销毁可信执行上下文 | 管理保护配置及可信状态，最小化可信计算基 |
| REE 客户端 | 提交请求、接收结果、提供非可信服务 | 客户端身份和参数均不能直接信任 |
| 可信应用 | 在受保护资源内执行业务 | 仅访问授权内存和显式通信接口 |
| 共享内存管理 | 分配、映射、复制和回收通信缓冲 | 所有权、长度、并发修改与生命周期 |
| 启动与证明 | 认证镜像、度量状态、生成报告 | 密钥根、重放防护及验证方策略 |

## 分阶段设计

1. 先建立威胁模型：可信组件、攻击者权限、DMA/调试口和中断假设。核对实验 CPU 的 PMP/ePMP 等硬件支持，不以架构名称推断具体芯片能力。
2. 对照 Keystone 的监控器模型、OP-TEE 的可信服务分工及其他 enclave 方案，记录隔离单元与调度权差异。外部实现是学习对象，不是本项目依赖。
3. 设计世界切换和异常处理，保证切换清理敏感状态、恢复寄存器，定义可信侧被中断和 REE 服务失败的行为。
4. 设计通信协议，明确长度校验、共享区映射、复制时机与回收。针对 TOCTOU、越界和重入编写验收场景。
5. 建立镜像认证和度量流程，再引入挑战/响应证明。区分“度量了什么”和“允许启动什么”。
6. 集成最小客户端与可信应用，逐项验证非法访问、退出清理、异常恢复及证明新鲜性。

## 接入 ZigguratOS 的约束

REE 侧可探索通过用户库和内核入口调用可信服务，但现有 syscall 表没有可信调用实现。OpenSBI 的机器级服务也不自动提供所需安全策略；任何固件集成须明确调用 ABI、内存所有权和错误处理。

无 MMU 小核运行可信内核任务这一事实不意味着任务隔离。若探索双核安全边界，还必须验证共享 DDR、总线主设备、启动固件和设备所有权；当前 Linux/小核排他保留约定服务于协作运行，未声称对恶意 Linux 安全。

## 完成判据

每个阶段须提交设计假设、保护配置证据、正常流程及负向测试。对越权访问和恶意输入的拒绝、敏感状态清理与密钥保护有可复现结果后，才能更新实现状态。外部项目和规格的版本应在实际实验记录中注明。
