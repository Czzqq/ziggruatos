# RISC-V 虚拟化设计路线

本文描述未来 hypervisor 实验。当前内核没有 Guest 入口、VM Exit、G-stage 页表或虚拟中断实现；现有 Sv39 用户页表与 SBI SMP 不能算作虚拟化完成。

## 计划模块与责任

| 模块 | 责任 | 核心约束 |
| --- | --- | --- |
| VM / vCPU 生命周期 | 管理客户机资源与运行状态 | 所有权、暂停、退出与回收 |
| CPU 虚拟化 | Guest entry/exit、CSR 与寄存器现场 | 区分主机和客户机权限，保证恢复完整 |
| 内存虚拟化 | Guest 物理内存及 G-stage 翻译 | 两阶段权限、TLB 无效化和越界拒绝 |
| 中断与时间 | 虚拟定时器、注入和中断路由 | 客户机时钟模型及屏蔽状态 |
| 虚拟设备 | MMIO 分发、虚拟串口与块设备 | 所有客户机输入都需校验 |
| 引导装配 | 客户机镜像、设备描述与固件接口 | 装载位置、可用内存与 SBI 责任 |

## 实验顺序

1. 选择支持 RISC-V H 扩展的 CPU/QEMU 配置，核对 HS/VS/VU 运行模式和相关 CSR。现有 `make run` 仅启动普通 virt 内核，不是 hypervisor 启动命令。
2. 最小 Guest 执行与退出：只验证受控程序入口、一次可解释 trap 和完整上下文恢复。
3. 建立 Guest 物理区域及 G-stage 映射，测试隔离、缺页与非法地址，定义两阶段翻译失败归属。
4. 实现虚拟时间与中断，区分主机时钟、客户机暂停和注入状态，避免把现有共享 jiffies 直接当客户机时钟。
5. 从简单虚拟串口扩展到 MMIO/VirtIO 设备模型，验证描述符地址、缓冲区长度、队列所有权与完成通知。
6. 定义 Guest 引导 ABI 并启动最小系统，再进行多 vCPU、回收与压力测试。

## 设计取舍

完全模拟设备便于隔离但增加处理成本；半虚拟化减少模拟复杂度，仍须验证所有客户机队列。设备直通还需要明确 DMA 隔离与中断重映射，不能仅靠 CPU 页表保证安全。

内存策略先采用明确归属的固定区域，以简化失败回收和隔离证明；按需分配、共享页和过量承诺属于后续设计。多 vCPU 需要额外的锁、TLB 同步与中断路由，不能从两 hart 普通调度直接继承完整正确性。

## 验收与资料

每阶段提供状态迁移、资源清单和可复现负向测试；最低验收包括客户机越权访问被拒绝、退出后主机现场正确、虚拟中断可控制和 VM 销毁无资源残留。构建成功不等于隔离成立。

阅读 RISC-V H 扩展/特权架构和 SBI 规范，并对照 KVM、Xvisor 等外部项目；这些不是仓库已有组件。相关：[系统设计](../obsidian/System-Design/1-System-Architecture-Overview.md)、[TEE 计划](ROADMAP_TEE.md)。
